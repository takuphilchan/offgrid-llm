# Server decomposition implementation evidence (2026-10-21)

The extraction operated on the already-dirty working-copy `server.go` recorded in `baseline-evidence.md`; it did not restore the committed version or start the installed service. Before extraction the file contained 6,170 lines, 113 functions/methods, 136 route registrations and five other top-level declarations. The current `server.go` contains 314 lines, `Server` and its existing progress types, plus the sole `Start` and `Close`. `rg` finds one `NewWithConfig` in `construction_legacy.go` and one `net.Listen` in `server.go`.

Concrete composition moved unchanged to `construction_legacy.go`; cache creation to `model_cache_startup.go`; model switching/admission to `model_runtime.go`; background helpers to `lifecycle_helpers.go`. The RAG startup closure was extracted to `startRAGAutoRestore`, called at its original point after llama startup, with the same wait-group accounting and cancellation. `router.go` holds 23 ordered private route groups and the original four outer wrappers. `middleware.go` and `exposure.go` own their respective checks. Former `server.go` handlers were split by capability into health/system, inference/terminal, model/cache/catalog/benchmark/quantization/hot-swap/load-balancer, download/USB/filesystem, user/quota/LoRA/plugin, agent/MCP, WebSocket, distributed RAG, template/UI and error files. No generic catch-all handler file or new subpackage was created.

The Go compiler and complete `internal/server` suite passed after the moves, so duplicate same-package definitions and missing identifiers are rejected. The route fixture still matches all 136 registrations and wrappers. Its test also checks that the 23 route-group calls occur in the same order as their source definitions; a live in-memory router construction/health test detects duplicate registration panics. Source layout alone does not prove live desktop or production-service behavior.
